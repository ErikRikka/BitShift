# Обновление мак-версии: что добавилось в Windows-версии (v2.6 → v2.9)

> **Как пользоваться:** мак-приложение собиралось по брифу, который описывал состояние
> **v2.6**. Здесь — **только то, что появилось после него**. Всё, что уже работает,
> трогать не нужно: ни один пункт ниже не отменяет прежнее поведение, все они
> добавляют новое либо чинят конкретный баг.
>
> Порядок важен: **пункты 1 и 2 — критические** (баг с потерей файла и баг, из-за
> которого не видно причину сбоя). Остальное — удобство.
>
> Приложение теперь называется **BitShift**.

## 🔴 1. КРИТИЧНО: многоканальный звук ронял кодирование

**Что случилось.** Файл `Capture0000.mov` (многокамерная концертная запись): ProRes 1280x720 50fps
плюс звук **pcm_s24le, 16 каналов** — многодорожечная запись концерта. Приложение
пережимало любой не-AAC звук в AAC и падало:

```
[aac] Unsupported channel layout "9.1.6"
```

Встроенный в ffmpeg AAC-энкодер **не умеет больше 8 каналов**. Файл не конвертировался
вообще.

**Решение — выбор пользователя.** Добавлен переключатель звука с двумя режимами:

| Режим | Аргументы ffmpeg | Смысл |
|---|---|---|
| **Оригинал · все каналы** (по умолчанию) | `-c:a copy` | Звук не трогается: все каналы, вся разрядность |
| **AAC стерео · компактно** | `-c:a aac -b:a 256k -ac 2` | Сводит в стерео |

Ключевой момент: **именно `-ac 2` снимает ограничение**. С принудительным стерео
16-канальный звук кодируется без ошибок.

Логика выбора (перенести как есть):

```
режим = «оригинал»                       # по умолчанию
если пользователь выбрал AAC:  режим = «aac»
если у файла стоит аварийный откат:  режим = откат

если режим == «оригинал»:                 -> "-c:a copy"
если исходник уже aac И каналов <= 2:     -> "-c:a copy"   # незачем перекодировать
иначе:                                    -> "-c:a aac -b:a 256k -ac 2"
```

Отдельное исключение с уже-AAC-стерео важно: без него повторное кодирование давало бы
потерю качества на ровном месте.

**Аварийный откат.** Экзотический звук может не лечь в контейнер результата. Если
кодирование упало, а звук копировался — **один раз** повторить с AAC, вместо того чтобы
терять файл целиком. Флаг ставится на конкретный файл, чтобы откат не зациклился.

**Проверять состав звука надо заранее** — одним вызовом, вместе с кодеком:

```
ffprobe -v error -select_streams a:0 -show_entries stream=codec_name,channels -print_format json ФАЙЛ
```

**Разница в размере огромна** — на том самом файле (75,4 ГБ, 77 минут):
- «Оригинал» → ~12 ГБ (из них ~10 ГБ — нетронутая многодорожка)
- «AAC стерео» → ~1,5 ГБ

Восьмикратная разница, поэтому это именно выбор, а не автоматика.

**Для DNxHR/ProRes-режима то же самое:** раньше звук жёстко приводился к `pcm_s16le`,
что резало 24 бита до 16. Теперь используется общая логика выбора.

## 🔴 2. КРИТИЧНО: в статусе показывалась не та ошибка

Приложение брало **первые 2 строки** stderr ffmpeg и выдавало их за причину сбоя.
В случае выше первой строкой было безобидное предупреждение:

```
[aist#0:1/pcm_s24le] Guessed Channel Layout: 9.1.6
```

…а настоящая ошибка (`Unsupported channel layout`) оставалась не видна. Я потратил
время на диагностику ровно из-за этого.

**Как надо:** искать в stderr строку, похожую на ошибку, а не брать первую попавшуюся.

```
взять все непустые строки
выкинуть строки с «Guessed Channel Layout»
оставить те, где встречается: error | unsupported | invalid | failed |
                              not supported | no space | denied | cannot | could not
если такие есть -> показать первые две
иначе           -> показать последние две (там обычно итог)
если файл пуст  -> «без сообщения»
```

## 🟡 3. Кодирование на месте, если файл уже на быстром диске

**Был баг.** После добавления мультивыбора папок кэширование включалось, если **хоть
одна** выбранная папка лежала на медленном диске — и тогда через кэш гнались вообще все
файлы, включая те, что уже на внутреннем SSD. Лишнее копирование в обе стороны впустую.

**Как надо:** решение принимается **по каждому файлу отдельно**.

```
если файл НЕ на медленном диске:
    кодировать на месте, без копирования (статус «на быстром диске — кодирую на месте»)
иначе:
    прежний путь через кэш
```

**Обязательно с мемоизацией.** Определение типа диска — дорогой системный вызов, а на
238 файлах он дёргался бы 238 раз. Ключ кэша — **корень пути** (том), а не путь целиком;
в пределах одного запуска диск не меняется. Сбрасывать кэш при старте прогона.

На маке тип диска определяется через `diskutil info -plist <точка монтирования>` →
поля `Protocol` и `SolidState`.

## 🟡 4. Оценка оставшегося времени

Блок «ОСТАЛОСЬ» рядом с «ОБЪЁМ».

**Считать по БАЙТАМ, а не по числу файлов.** Это принципиально: в одной папке у
пользователя лежат и файлы по 100 МБ, и по 9 ГБ. Счёт по штукам врал бы в разы.

```
сделано_байт = байты завершённых файлов
             + сумма(размер × процент/100) по файлам в работе
прошло       = сейчас - начало прогона

если прошло < 20 с или сделано == 0:  «считаю…»      # рано, оценка будет чушью
доля = сделано_байт / всего_байт
если доля >= 0.999:                   «завершаем…»
осталось = прошло × (1 - доля) / доля
```

**Сглаживание обязательно**, иначе метка дёргается на каждом тике:

```
если первая оценка:  сглаж = осталось
иначе:               сглаж = сглаж × 0.75 + осталось × 0.25
```

**Хвост.** Когда кодирование закончилось, но файлы ещё ждут проверки/переноса — не
показывать «меньше минуты», если в очередях что-то есть; поднять оценку минимум до 20 с.

Формат вывода: `меньше минуты` / `~7 мин` / `~1 ч 30 мин` / `~1 дн 2 ч`.

Проверено на числах: 10 ГБ из 100 за 10 минут → «~1 ч 30 мин»; при скачущем входе
(25→26→24→27 ГБ) метка держится ровно: 30/30/30/29/30 мин.

## 🟡 5. Несколько папок за один запуск

Раньше — одна папка. Теперь список корней, обходятся все.

- Список пустой = работать по единственной папке (так продолжают жить тест-хуки).
- Первый корень считается «основным».
- **Если выбрано больше одной папки — к имени файла в списке спереди добавлять имя
  корневой папки**, иначе строки не различить: `C0008.MP4` из одной съёмки и из другой
  выглядели бы одинаково.
- Кэширование включать, если хоть один корень на медленном диске (но дальше — пофайлово,
  см. п. 3).
- В счётчике показывать число папок: `238 файлов · папок 2 · кодек AV1`.

На маке в CLI это просто несколько путей аргументами.

## 🟢 6. Прогресс по каждому файлу на всех этапах

Раньше прогресс был только общий. Теперь у каждого файла своя шкала, **на всех четырёх
этапах**, у каждого свой цвет:

| Этап | Как считать прогресс |
|---|---|
| Копирование на быстрый диск | по росту размера файла-назначения |
| Кодирование | из `-progress` ffmpeg: `out_time_us` / длительность |
| Проверка | так же из `-progress` (**раньше его тут не было — добавить**) |
| Перенос результата | по росту размера файла-назначения |

Полезная мелочь: при запуске проверки надо запомнить длительность результата — она нужна
как знаменатель для процента.

Для CLI это строка вида `[кодирование ▓▓▓▓▓░░░░░ 52%]` на файл.

## 🟢 7. Мелочи

- **Режим «Исходники шоу» убран** — осталось три: «Старые ролики», «Съёмка S-Log3»,
  «Домашний архив / Reels». По умолчанию теперь «Домашний архив / Reels».
  *(В мак-брифе была таблица из 4 режимов — удалить третью строку, остальные параметры
  без изменений.)*
- **Автоудаление в Корзину — по умолчанию ВКЛЮЧЕНО** (прямая просьба пользователя от
  2026-07-21). Само правило «только в Корзину и только после полной проверки» —
  без изменений, не ослаблять. **На маке я бы всё равно оставил ВЫКЛ до тех пор, пока
  Корзина не проверена на внешнем диске** — см. протокол в основном брифе.
- **Название BitShift**, иконка — тёмный знак: зелёное кольцо, красный круг на 8 долек,
  хвост девятки. На размерах меньше 32px мелкие детали не рисовать, иначе каша.
